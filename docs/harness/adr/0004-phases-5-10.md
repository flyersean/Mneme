# ADR 0004 — Recovery, self-improvement, profiles, control plane, jobs, gateways, swarm (Phases 5–10)

Status: accepted (2026-09-28).

## Phase 5 — verification & recovery

- **Every failed step gets a deterministic category** (`failures.classify`):
  `verification`, `unexecutable`, `empty`, `fabricated`, `provider`, `budget`,
  `rejected`, `executor_error`, `tool`, `interrupted` or `other`. It is stored in the
  step's meta and in the `task_failed` event, and feeds metrics and reflection. The
  model's own explanation is never used to categorize.
- **An `llm_judge` check supplements deterministic checks and never replaces them.**
  It runs only after every deterministic check has passed, so a judge cannot rescue
  work that failed an objective check.
- **Approval is per task.** A task needs it when it carries `requires_approval`, or
  when the run's profile sets `approve_each_task`. Such a task parks the run in
  `awaiting_approval`, which counts as not active: no owner, and not an orphan.
  - approve: the task is marked approved and the run resumes.
  - reject: the task fails with "rejected by …" and the run replans (or fails if
    there is no planner).

  Approval is *not* per tool call: pausing inside `process_chat`'s synchronous tool
  loop would need a re-entrant turn. Per-tool control is the permission grant (ADR 0003).

## Phase 6 — self-improvement

- **Every system change is a proposal** with a kind, target, content, reason,
  evidence (run ids), tests and level. The `proposals` table and the append-only
  `evolution_log` (enforced by triggers) answer two questions: why an object is the
  way it is, and what it looked like before.
- **Levels:**

  | Level | Kinds | How it is applied |
  |---|---|---|
  | L1 | knowledge | automatic |
  | L2 | skill, strategy | automatic, versioned |
  | L3 | instruction, profile, config | tests must pass, plus an explicit approval (`actor="auto"` is refused) |
  | L4 | code | a `git worktree` on branch `evolve/<id>`, with the patch applied and tested there |

  **L4 is never merged automatically**; activation is a human `git merge`. Code
  proposals without tests are refused. A proposal may raise its level but never
  lower it.
- **Apply is transactional.**
  1. Capture the previous content.
  2. Apply the change.
  3. Re-run the tests.
  4. On failure, restore the previous content, mark the proposal `rolled_back`, and
     keep the attempt.

  Skill restores are new versions, so history is never rewritten.
- **Hooks.**
  - `observe_run`: every failed run, or run that recovered from failures, becomes an
    L1 knowledge note. The note is also staged into Mneme memory, so the lesson can
    be retrieved next time.
  - The reflection turn (`LESSON:` / `SKILL:` tags) is **off by default**
    (`harness.reflect`) because it costs a model call per such run.

## Phase 7 — profiles & artifacts

- **A profile selects within the harness; it never replaces it.** A profile has:
  - skills, which are pinned into the capability context;
  - a grant;
  - budget defaults;
  - a `plan` default;
  - an `approve_each_task` setting.

  Explicit run arguments always win over the profile. Profiles are versioned, and
  L3 proposals can change them.
- **Artifacts:** files left in `runs/<id>/artifacts/` are registered automatically
  when a run ends (with a checksum and `provenance.captured=auto`).

## Phase 8 — control plane

- **`/`-commands have the same authority model as `<<…>>`:** they are typed by the
  user and handled by the harness, never by the model.
  - Unknown `/words` fall through to the model, so `/usr/bin …` still reaches it.
  - Commands are ignored inside a harness step. That prevents a task titled
    `/run …` from recursing.
- **Dashboard:** one static page (`/runs/ui`) evolved from the existing style. It is
  not a new UI system.
- **Metrics are derived from the ledger**, so they cannot drift from "what happened".
  They are collected, not optimized.

## Phase 9 — jobs & gateways

- **A job fires on a compare-and-set of `next_run_at`**, so proxies sharing a ledger
  never double-fire. By default a job does not overlap itself: a tick is skipped and
  recorded when the previous run is still active.
- **Gateways are extensions, and HTTP-only.** The core never learns which interface
  a message came from; the gateway's identity string (`telegram:<id>`) is the actor.
  Telegram refuses to start without an allow-list and answers private chats only.
  The name `proxy/gateway.py` (the reverse proxy) is left as it is.

## Phase 10 — swarm

- **The swarm stays an extension.** It records itself through an **external** run,
  which the harness records but never executes, recovers, resumes or retries.
  Extensions may write events and status **only** to external runs, so the harness's
  own event stream stays trustworthy.
- **Each step event records the *next* step.** Resuming then needs no re-evaluation
  of `if` conditions on outputs that were never persisted.
- **Recording is optional and non-fatal by default.** A swarm must not break because
  the proxy is down, unless `harness.required` is set.
